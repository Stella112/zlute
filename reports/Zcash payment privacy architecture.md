# Shielded Zcash hides payments, not the people making them

No Zcash payment product reaches "100% privacy", and none of the serious ones claim to. Shielded transactions in the Ironwood pool hide the sender, the recipient, the amount and the memo from the public blockchain. Four things still leak: transaction timing, fees and shape; any amount that crosses between pools; everything the wallet's sync server can see (your IP address, when you sync, what you broadcast); and everything a custodian or viewing-key holder can see. The products with the strongest privacy (Zodl/Zashi, Zingo, Zkool, Keystone hardware signing) keep spending keys on the user's device. The merchant tools that work (CipherPay, the BTCPay Zcash plugin, ZECATHON's ZecCheckout) give the server only a viewing key, so it can see payments arrive but cannot move money. For Lute this has one blunt implication. Today Lute is a custodial service: the operator can read every wallet and could spend from it. The browser approval key stops other people from spending, but it does not stop the operator. In the two days before the 28 October deadline, Lute cannot honestly become non-custodial. It can make its custody and privacy claims exact, shrink what it logs and leaks, and make sure its invoices follow best practice. The real fix is a "server builds, browser signs" design using PCZT, the standard format for partly built Zcash transactions. That design turns the browser key into the actual Zcash spending key. It is a few weeks of work, and it is the right headline for the roadmap.

## The plain-language version for a founder

Think of a Zcash payment as passing through three layers, each with its own audience. The **blockchain** is public. Shielded payments make it very private: outsiders see that some transaction happened at some time and paid a standard fee, but not who paid whom or how much. The **network** layer comes next. Your wallet has to talk to a server to learn about new blocks and to send transactions, and that server sees your internet address, when you show up and what you send, much like a postal worker who cannot open the letters but knows your house. The **operator** layer is whoever runs the software holding your keys or viewing keys. For a hosted web app that is the company itself, and it can see everything it processes.

Every Zcash product chooses how to handle those three layers. Phone wallets like Zodl keep the keys on the phone, so there is no operator, and they offer Tor to blur the network layer. Merchant tools give the hosted service a read-only "viewing key", so the operator sees incoming sales but can never take the money. Lute currently holds the full keys on its server. Its browser approval key is like a second signature that Lute's own software checks; it is not a lock the blockchain itself enforces.

The best architecture for a hosted, wallet-free web app keeps the shielded on-chain privacy. It splits the work so that the server prepares each transaction and the user's browser holds the only key that can sign it. It runs its own blockchain server, so no outside company sees users' activity. It sends transactions over Tor. And it says plainly, in writing, what the operator can still see. Lute can do the honesty and hygiene parts this week. The key split is the next milestone.

## Self-custody wallets keep keys local but leak to their sync server

All the mainstream shielded wallets are light clients that never hand over spend authority: Zodl (renamed from Zashi in February 2026 when the team left ECC to form ZODL), YWallet and its successor Zkool, Zingo, Nighthawk, Unstoppable and Edge ([Forklog](https://forklog.com/en/news/zcash-developers-establish-new-entity-and-rebrand-wallet); [Coin Bureau](https://www.coinbureau.com/analysis/best-zcash-wallets)). Each wallet downloads compressed "compact blocks" from a lightwalletd or Zaino server and tries to decrypt every output locally with its own keys. The Zcash light-client spec says this stream "leaks no information about which transactions the light client is interested in" ([ZIP 307](https://zips.z.cash/zip-0307)). The same spec then lists the gaps. **The height a wallet starts syncing from is "an information leak"**, and the proposed fix (rounding heights into buckets) "has not been implemented". Fetching a full transaction, for example to read a memo, reveals which transaction the wallet cares about. Unlinkability holds only "if network privacy such as Tor is assumed". The spec "does not address how to spend notes privately" ([ZIP 307](https://zips.z.cash/zip-0307)). Nym's threat model treats the light-client server as the main adversary. Without protection, that server sees the "Real client IP", "Every request and every broadcast" and "All request timing and content" ([Nym docs](https://nym.com/docs/network/threat-model/examples/wallet)). Nighthawk's own listing warns that broadcast privacy "cannot be guaranteed" ([F-Droid](https://f-droid.org/en/packages/com.nighthawkapps.wallet.android/)).

The wallets differ mostly in how they shrink that network leak. **Zodl offers opt-in "Beta" Tor** for sending, fetching transaction data, exchange rates and third-party APIs. Without it, CoinMarketCap sees the user's IP on every price lookup. Zodl's support article does not say whether block sync itself goes over Tor ([Zodl support](https://support.zodl.com/article/17-enabling-tor-protection); [Zodl currency conversion](https://support.zodl.com/article/27-enabling-currency-conversion)). **Nym's mixnet went live on 24 September 2026 in Zingo and Zkool**, but not in Zodl. Nym's own docs call mixnet sync "very slow (5-hop + mixing delays)", and its roadmap calls the mixnet "simply too slow for everyday usage" ([Nym blog](https://nym.com/blog/nym-mixnet-zcash-wallets); [Nym roadmap](https://nym.com/blog/nym-roadmap-2026)). YWallet and Zingo let users point at their own server ([ZecHub](https://zechub.wiki/zcash-tech/lightwallet-nodes)). Running your own server removes the third party but not the problem: your own Zebra node still announces transactions to the peer-to-peer network, and Zcash "does not obfuscate IP addresses" ([Zcash docs](https://zcash.readthedocs.io/en/latest/rtd_pages/privacy_recommendations_best_practices.html)). Swapping lightwalletd for Zingo Labs' Zaino indexer changes the software, not the trust model, because Zaino speaks the same protocol to the same operator.

Hardware wallets push key isolation furthest. Zodl pairs with a Keystone running its "Cypherpunk" firmware, which signs shielded transactions on the device. Least Authority audited it in March 2025 ([Zodl support](https://support.zodl.com/article/33-connecting-a-keystone-wallet); [Least Authority](https://leastauthority.com/blog/audit-of-keystone-hardware-wallet-for-zcash/)). Ledger's Zcash signer kit exports a full viewing key and returns only spend signatures, while the host builds the transaction ([Ledger docs](https://developers.ledger.com/docs/device-interaction/dmk-ts/references/signers/zcash)). Trezor does not support shielded Zcash ([Trezor](https://trezor.io/coins/detail/zcash)).

## Merchant tools converged on viewing keys and one address per invoice

Shielded merchant processing has settled on one pattern. The merchant keeps the spending key in their own wallet. The payment server gets a viewing key, generates a fresh shielded address for each invoice, and watches the chain. **BTCPay's Zcash plugin tells merchants to "Setup Your (View-Only) Zcash Wallet"** by exporting a viewing key from YWallet or Zingo. It also warns that one instance "shares a single Zcash wallet across all the stores", which makes it unsafe on shared hosting ([BTCPay plugin docs](https://github.com/btcpay-zcash/btcpayserver-zcash-plugin/blob/master/docs/installation.md); [repo](https://github.com/btcpay-zcash/btcpayserver-zcash-plugin)). **CipherPay**, the most mature hosted option, is live on mainnet with WooCommerce and Shopify plugins, subscriptions and an x402 package. It describes itself as non-custodial, but its viewing key "means the server can see your incoming payments, which invoices got paid, how much, when". Merchants who want zero hosted visibility can self-host it from a single binary ([CipherPay forum](https://forum.zcashcommunity.com/t/cipherpay-yes-another-zcash-payment-processor-sorry-live/54830)). NOWPayments, Plisio and Binance Pay process only transparent ZEC, so they offer roughly Bitcoin-level privacy whatever they say about custody ([ZecHub processors](https://zechub.wiki/payment-processors)).

Which viewing key the server gets matters more than most products admit. A **unified full viewing key (UFVK) shows everything, incoming and outgoing**: its outgoing component recovers "destination address, amount, and memo" of every payment the merchant sends. A **unified incoming viewing key (UIVK) shows only incoming payments**, not change or spending ([ZIP 316](https://zips.z.cash/zip-0316)). Neither can spend. A server that only needs to detect payments needs only the UIVK. Even so, most tools, ZecCheckout included, ask for the UFVK and over-disclose the merchant's outgoing activity ([ZecCheckout](https://github.com/samizdatproject/zeccheckout)). Monero's merchant tools follow the same view-key-plus-subaddress design, and AcceptXMR "needs no hot wallet" ([docs.rs acceptxmr](https://docs.rs/acceptxmr)), which suggests this is simply the right shape for private-coin checkout.

The invoice flow itself is well standardized. **ZIP-321** defines the `zcash:` payment link with address, amount, a base64url memo of up to 512 bytes, and multi-recipient support. It forbids memos to transparent addresses, and it has no standard field for an expiry or invoice ID ([ZIP-321](https://zips.z.cash/zip-0321)). ZECATHON's ZecCheckout shows current best practice. Each invoice gets a diversified Unified Address with only Orchard/Ironwood and Sapling receivers, so payers cannot fall back to transparent. Payments are matched by the diversifier index recovered from the decrypted note, not by memo. The tool never calls `GetTransaction`, so the sync server cannot tell which transactions are the merchant's. It defaults to 3 confirmations, recommends 10 or more for large mainnet amounts, and treats a mempool sighting as a hint that never changes invoice status. It found that a public lightwalletd held only 4 of 18 mempool transactions a node had seen ([ZecCheckout](https://github.com/samizdatproject/zeccheckout)). Those depths match ZIP-315's 3 trusted / 10 untrusted guidance ([ZIP-315](https://zips.z.cash/zip-0315)). ZecCheckout also names a trust point most products skip: it does not verify proof-of-work, so **a malicious lightwalletd could fake a "paid" status**. Running your own node, or checking against several servers, closes that gap.

Fees are a small but real fingerprint. ZIP-317 charges 5,000 zatoshis per logical action with a minimum of two, so the cheapest shielded payment costs 0.0001 ZEC. The ZIP warns that "non-standard fees may reveal specific users, wallets, or wallet versions" ([ZIP-317](https://zips.z.cash/zip-0317)). Use the library's default fee and default expiry, and remember that sweeping many small invoice notes into one transaction publishes the note count through the action count.

## On-chain privacy is strong, but the Ironwood turnstile and pool edges still leak

Inside one shielded pool, a transaction still exposes its block time, fee, number of actions, expiry height, anchor and net value balance. **Any value that crosses a pool boundary is public in amount and time** ([ZIP 317](https://zips.z.cash/zip-0317); [Fireblocks](https://support.fireblocks.io/hc/en-us/articles/26026114047900-Zcash-ZEC-transactions-on-Fireblocks)). That matters right now. A soundness bug in the Orchard circuit, found on 29 May 2026, could have allowed undetectable counterfeiting. NU6.3 activated on 28 July 2026 at block 3,428,143, opened the new Ironwood pool and made Orchard withdraw-only through a turnstile ([z.cash NU6.3](https://z.cash/upgrade/nu6-3/)). Migration amounts are visible. Zodl warns that moving a whole balance in one transfer publishes "the most identifying number you could put on chain" ([Zodl support](https://support.zodl.com/article/62-migrating-to-ironwood-self-migration)). Draft ZIP 318 splits balances into 1/2/5 denominations and adds random delays averaging about 82 minutes. Even so, it says outright that it is not provably leak-free ([ZIP 318](https://zips.z.cash/zip-0318)). About 89.5% of Orchard value had migrated by late September ([zecstats](https://zecstats.org/ironwood)).

The research record points the same way. Deanonymization has come from behavior at the transparent boundary, not from broken cryptography. Kappos et al. (USENIX Security 2018) deanonymized **69.1% of transactions that touched the shielded pool** using round-trip amounts and miner and founder patterns, but found no obvious attack on fully shielded z-to-z payments, which were then under 1% of traffic ([USENIX](https://www.usenix.org/conference/usenixsecurity18/presentation/kappos); [slides](https://www.usenix.net/sites/default/files/conference/protected-files/security18_slides_kappos.pdf)). Tramer, Boneh and Paterson showed that timing a user's node could identify payees, a flaw that has since been patched ([USENIX 2020](https://www.usenix.org/conference/usenixsecurity20/presentation/tramer)). Biryukov et al. described "tagging" attacks that send small marked amounts and watch for them to leave ([orbilu](https://orbilu.uni.lu/handle/10993/41278)). These figures come from a Sprout-era, mostly transparent chain and should not be read as today's Ironwood rates. The notes found no 2024–2026 measurement study, which is itself an open uncertainty. The lesson carries over anyway. Privacy fails at the edges: shielding and deshielding, round amounts, timing, published txids, and memos read by counterparties. Railgun shows the same thing on Ethereum. In a 2026 study, 1,049 of the gas-payer addresses behind 6,856 self-broadcast withdrawals were also depositors ([arXiv 2606.25926](https://arxiv.org/pdf/2606.25926)).

## Browser wallets are stuck, but PCZT lets the server build and the browser sign

A fully in-browser Zcash wallet is not viable for Ironwood today. **ChainSafe's WebZjs is the only real browser library.** It is unaudited (only the MetaMask Snap built on it was audited), it needs a gRPC-web proxy in front of lightwalletd, and its last public commits (April 2026) pin a librustzcash fork at NU6.1 with no sign of NU6.3 or Ironwood support ([WebZjs](https://github.com/ChainSafe/WebZjs); [Cargo.toml](https://raw.githubusercontent.com/ChainSafe/WebZjs/main/Cargo.toml); [commits](https://github.com/ChainSafe/WebZjs/commits/main)). ChainSafe's own design notes call the approach "explicitly not for production", warn that sync can take "several minutes or potentially hours", and say transaction creation needs the seed in the page ([HackMD](https://hackmd.io/@wollum/BJaqaB81kl)). A browser cannot protect such a seed well either. WebCrypto has no Jubjub or Pallas signing, so the raw key must sit in JavaScript or WASM memory. A host that serves malicious JavaScript defeats any in-page "non-custodial" claim unless the code is pinned or moved into an extension, a Snap or a hardware wallet.

The workable split is PCZT, the format for partly built Zcash transactions, whose stated goal is a format that "must not require spending key material to be present" ([ZIP 374](https://zips.z.cash/zip-0374)). The crates Lute's sidecar already uses support it. `zcash_client_backend::create_pczt_from_proposal` has existed since 0.16.0. Version 0.24.0 (18 August 2026) added Ironwood, NU6.3 fee rules and signer-view redaction helpers, and 0.25.0 (21 October 2026) added recipient-address expiry ([CHANGELOG](https://raw.githubusercontent.com/zcash/librustzcash/main/zcash_client_backend/CHANGELOG.md)). The `pczt` 0.10.0 Signer exposes `sign_ironwood(rng, index, ask)`. Its default `SighashPolicy::ALL_ONLY` stops a signer from signing transactions it did not review ([pczt signer](https://raw.githubusercontent.com/zcash/librustzcash/main/pczt/src/roles/signer/mod.rs)). **Ironwood proofs need only the full viewing key, not the spending key.** So the server can hold a UFVK, propose and prove the transaction, redact what the signer does not need, and send it to the browser. The browser checks the decoded recipient, amount and fee, signs with the spend-authorizing key `ask`, and sends the signed PCZT back for the server to finalize and broadcast. The browser avoids sync, Halo 2 proving and the 51.5 MB Sapling parameters. This is the model Keystone and Ledger already use. The cost is that the server still sees everything a UFVK holder sees, so the operator keeps visibility but loses the ability to spend. The notes estimate this at a few engineer-weeks: one to two weeks for a WASM signer, about a week for sidecar endpoints, and about a week for review UI, key storage and backup. Those estimates are researcher judgment, and no public case study of a web app using this exact split exists yet.

FROST threshold signing could later let the server hold one share and the user another, but production wallet support is thin: only Zkool is reported to support it ([ZecHub Vol.5](https://zechub.substack.com/p/zcash-shielded-news-vol5-9a8)).

## AI agents on Zcash keep keys out of the model and batch settlement

Coinbase's x402 has no Zcash scheme. Each (scheme, network) pair must be added explicitly ([coinbase/x402](https://github.com/coinbase/x402)). Zcash x402 support comes from third parties. CipherPay's `@cipherpay/x402` verifies payments by trial decryption and offers prepaid sessions ([jsDelivr](https://www.jsdelivr.com/package/npm/@cipherpay/x402)). Kage (zec-shielded-x402) runs on testnet only. Its merchant facilitator holds just a UIVK, checks a memo nonce against each challenge, returns signed receipts with an empty payer field, and sells blind-RSA "tabs" so later requests cannot be linked to the payment. It reported 10 testnet payments, two started by an LLM over MCP ([Kage repo](https://github.com/nickthelegend/zec-shielded-x402)). Agent-wallet grant proposals with mandates and spending caps did not get funded: Shielded x402 was declined and ZAgentPay was closed on process grounds ([ZCG #445](https://github.com/ZcashCommunityGrants/zcashcommunitygrants/issues/445); [ZCG #466](https://github.com/ZcashCommunityGrants/zcashcommunitygrants/issues/466)). The design the community keeps converging on has three parts. The model never sees keys, a policy engine outside the model enforces budget, per-payment cap, expiry, allowlist and human approval, and verification uses viewing keys. A 0.0001 ZEC fee floor and minute-scale block times make per-call on-chain settlement uneconomic, so prepaid sessions or batching are required. **No mainnet shielded x402 deployment was independently confirmed.** That leaves Lute's metered, batched agent payments in thin company, which is a differentiator as long as the custody disclosure stays explicit.

## What Lute should do, ranked by feasibility

Lute's current state, according to its own `docs/CUSTODY.md`: each wallet's seed is sealed on the server with a key file readable by root. The sidecar spends only when the user's browser-held Ed25519 key, or a signed mandate, approves the exact transaction. Users cannot recover funds if Lute disappears. That makes Lute custodial with software-enforced approvals. The approval key really does protect against a compromised API, a prompt-injected agent and replayed approvals. It does not protect against the operator. The options below are ranked from most to least feasible. The first group fits in two days. The second is roadmap.

| Rank | Option | Fits in 2 days? | What it buys | Main risk or cost |
|---|---|---|---|---|
| 1 | Make every privacy and custody claim exact: no "100% private" or "untraceable"; publish a who-sees-what table (public chain, sync server, operator) | Yes, copy only | Credibility with judges; matches how ZIP 318, Zodl and the Zcash docs word their claims | None |
| 2 | Invoice hygiene check: a fresh shielded-only UA per invoice (no transparent receiver), match by diversifier index not memo, no `GetTransaction` per invoice, 3 confirmations by default and 10 for large amounts, default ZIP-317 fee and expiry, mempool shown only as a hint | Yes, if mostly a verification pass | Removes the most common on-chain and server-side leaks | Any rework found late in the window |
| 3 | Metadata minimization: proxy access logs off, no txids, addresses or memos in webhook payloads or app logs, short retention | Yes | Shrinks what a server breach or subpoena reveals; the measured leaks in Railgun came from metadata | Low; mind the existing VPS log caps |
| 4 | Watch-only "bring your own wallet" receiving: the merchant pastes a UIVK from Zodl, and Lute imports it as a watch-only account and only detects payments | Stretch | Funds go straight to the user's own wallet, so Lute is non-custodial on the receive side and cannot see outgoing spending | New account type and UI under deadline pressure; demo with a clear "beta" label |
| 5 | Broadcast over Tor from the sidecar (the `zcash_client_backend` Tor module) or through a second server | Stretch, likely roadmap | Breaks the link between the server's IP and broadcasts | Build and runtime risk; no on-box Rust builds on the shared VPS |
| 6 | PCZT "sidecar builds and proves, browser signs": the sidecar keeps only UFVKs, and the browser key becomes the Ironwood `ask` | Roadmap, a few weeks | Lute becomes non-custodial for spending; the operator can see but not spend | Needs a WASM signer, a review UI that decodes outputs, seed backup UX, a pinned frontend and an external review |
| 7 | Own Zebra plus Zaino/lightwalletd | Roadmap | No third-party sync server; a node that checks proof-of-work against fake "paid" signals | Disk and sync time on the shared VPS; P2P broadcast still needs Tor |
| 8 | Hardware signing (Keystone) and FROST shares for recovery | Roadmap | Strongest key isolation; escape hatch if Lute disappears | Thin FROST wallet support; firmware support for Ironwood unverified |
| 9 | Full in-browser wallet (WebZjs) | Not recommended | Would hide activity from Lute | No NU6.3/Ironwood support, unaudited, slow sync |

For the hackathon, items 1–3 are cheap and defensible. Item 4 is the one stretch worth attempting, because it turns "custodial" into "non-custodial for receiving" on a real feature without touching the spend path. Item 6 should be the roadmap headline. It reuses functions Lute's existing crates already ship, and it changes the custody answer from "the operator could spend" to "the operator can see, but only your browser can sign". Until it ships, Lute should keep saying it is custodial.

## Conclusion

The research reframes the question. "How private is Zcash?" has a good answer: very, on-chain, inside one shielded pool. The question that decides a hosted product is "who besides the chain is watching?", and the honest answer is a short, named list: the sync server, the network path, and whoever holds keys. Products earn trust by shrinking that list and publishing it. They lose it by claiming the list is empty. That puts Lute's 2-day priorities in exact language and less metadata, not in new cryptography.

The more surprising finding is how little separates Lute from a credible non-custodial design. The PCZT functions, Ironwood signing and signer-safety defaults already ship in the librustzcash releases Lute's sidecar depends on. The browser approval-key UX Lute already built is the same user experience a "browser signs" model needs. The roadmap step is not a rewrite. It moves the key Lute's software currently checks into the one key the blockchain itself checks.
